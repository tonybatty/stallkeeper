## Commands

`pnpm dev` starts both apps. With `DATABASE_URL` unset it also starts embedded Postgres on port 54329, keeping its data in `apps/api/.pgdata`; delete that folder to start again. Plain SQL migrations in `apps/api/migrations` run in name order at every API start. `pnpm build` builds both apps. `pnpm test` runs mocked tests against a throwaway embedded Postgres, with a fresh database per test file. CI runs `pnpm typecheck`, `pnpm lint`, `pnpm test` and `pnpm build`. Use Node 22.22.0, install the pinned pnpm with `npm install --global pnpm@12.6.0`, then run `pnpm install --frozen-lockfile`. Do not use the bundled Corepack for pnpm 12; see Services above. After `pnpm build`, `pnpm --filter @stallkeeper/api start` runs the one service the way Render does: the API serves the built web app, and every path outside `/api` falls through to it. In `pnpm dev` Vite proxies `/api` to the API on `PORT`, default 3000, so the browser sees one origin there too.

## Judge-period watch

`GET /api/health` returns `{ "status": "ok", "commit": "<sha>" }`. The commit comes from `RENDER_GIT_COMMIT`, which Render sets on each deploy, and reads `unknown` when the variable is unset, as it is locally. It is the way to tell which build is deployed after an API-only change, which leaves the web bundle name the same.

`.github/workflows/demo-watch.yml` runs daily and on demand. It uses no secrets and makes three plain GET requests: it checks that `/api/health` reports `ok` with a commit, and that `/api/demo` lists at least one haggle item whose availability is `available`. It sends no chat turns, logs in nowhere and makes no payments. A failing run makes GitHub email the repository owner. It does not check that chat or PayPal work, only that the service is up and the demo stall is stocked.

## Comparable new prices

Set `CHANNEL3_API_KEY` to enable the owner's price lookup. The API calls Channel3 through `@channel3/sdk` with `country=GB`, `language=en` and `currency=GBP`: `POST /v1/search` for text lookup (`POST /api/owner/retail/lookup`), `POST /v1/image-search` with the compressed JPEG as `base64_image` when the owner adds or replaces a photo (`POST /api/owner/retail/image-lookup`), and `GET /v1/products/{id}` to read a chosen product back when an item is saved. Together these are limited to 30 an hour per stall. Past that limit the item still saves, without a new reference. The browser sends photos only to the owner API and never receives the Channel3 key. When saving an item it sends only a product ID and whether the lookup flagged that match as doubtful, never a price or listing text. The server fetches that product's offers itself and stores the lowest in-stock new GBP offer, with the product ID, retailer, link, offers and check date, in `items.retail_ref`. Offers in another currency, out of stock, or without a new condition are never used, and nothing is converted.

A buyer's item page and each chat turn read that snapshot. When it is older than ten minutes the API refreshes it with the product lookup first, waiting three seconds at most, and tries an item again no sooner than five minutes later. If Channel3 fails, the stored snapshot is shown with its date for up to seven days, then nothing. If Channel3 reports the product as not found, or the lookup finds no usable new offer, nothing is shown. Only an item on sale refreshes. A sold or reserved item, or any unsold item while the stall is closed, shows its stored snapshot with its checked date and makes no Channel3 call. A removed item shows no reference. The chat prompt gets the same figure as wording ("New from GBP 64.00 at retailer, a shop's listed price for a new one"), and it passes the reply amount check through `pricePence`. A failed lookup never blocks saving or paying, and no reference is shown unless Channel3 returned it.

Each candidate's reference also carries the listing's details, from the same search response with no extra Channel3 call: the product description, up to 600 characters, and up to eight `facts`: brand, materials, key features, then structured attributes, in that order, each under 120 characters. The server reduces listing text to plain text, strips markup, drops any "condition" attribute, and cuts long fields. Listing text that mentions a price is kept as written, and the reply amount check below is the only price guard. The lookup sits behind one "Check the new price online" link on the form. After the owner chooses a match, and on the edit form for a saved reference, the form shows the details read-only under "From the retailer's listing for a new one", with the line "Stallkeeper AI can use these when answering buyers, as the retailer's details for a new one." With none, it says the listing has no details. Saving sends no listing text: the server reads the product back and stores its details in `items.retail_ref` with the price, and each refresh replaces them with Channel3's current ones. Removing the reference removes them. The chat gets them only while the reference itself is shown: when a refresh finds the product gone, or the snapshot is too old to show, the chat gets neither the price line nor the details. A doubtful match, one whose title lacks a searched word, carries no details: the lookup returns none for it, the form says "If you use it, Stallkeeper AI will not use this listing's details when answering buyers." beside it, the form sends `retailDoubtful: true` with the product ID, and the server stores the reference as `doubtful` with an empty description and no facts, on save and on every refresh. A save that names a product without `retailDoubtful`, such as one from a form loaded before the field existed or a direct API call, is treated as doubtful too; the form sends `false` for a sound match, and the demo reset does the same for its two hand-picked products. Its price line works as for any other match. A reference stored before the `doubtful` field existed has no such key and is treated the same way: it keeps its price line and gains no description or facts, on refresh as well, until the owner next picks the match on the form, where the edit form says "Stallkeeper AI does not use this listing's details. To change that, search again and choose a match." The chat prompt gets them as `retailListingForNewOne`, separate from the owner's notes. The AI stallholder is told to attribute them ("the retailer's listing for a new one says"), never to present them as this item's condition, to answer condition, damage and whether it works only from the notes, and to prefer the notes when the two disagree. Buyer pages never carry them. Tests cover this with mocked Channel3 responses and a mocked model; it has not run against real Claude. Before this, a fact reached the AI only when the owner pressed "Add to notes"; one hosted run of that flow on 7 November 2026 is recorded in [EVIDENCE.md](EVIDENCE.md#channel3-listing-facts-on-the-hosted-service-7-november-2026).

The owner decides whether a candidate matches. The form shows "No useful reference found" when no candidate has a usable GBP new offer, or when the owner chooses "None of these match", which clears only the current search selection: it leaves the price fields alone, stores no new reference and keeps any reference saved earlier.

On the demo stall, a reset also saves a reference for two seeded items, the round wall mirror and the wooden stool, from fixed product IDs. The lookup runs after the reset commits, so it cannot roll the reset back or leave the stall without stock, but the reset call waits for it, three seconds at most. A failure leaves those items without a reference until a later reset. The references appear on the hosted service at the first demo reset after a deploy, whether the nightly or idle reset or a Reset stall button, not on the deploy alone.

The suggested asking price is half the lowest new price rounded up to 50p, and the suggested floor is two thirds of that, rounded up to 50p. Both are starting points the owner can change. A listing whose title lacks a word from the search, ignoring words that describe wear or a count, such as "chipped", "vintage" or "six", is shown with a warning naming those words and carries no suggested prices, because its price may belong to a different kind of item. The owner can still use it as the reference for the price line, and its listing details are not stored or given to the AI stallholder. A photo search has no words to compare, so its candidates carry no warning and every one with a new price carries suggested prices. A retailer's listing is not a second-hand sale price or a valuation, and the copy says so.

## Item photos

Set `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` in the API environment to enable photos. Create a private Storage bucket named `item-photos`, restricted to `image/jpeg` with a 512 KiB file limit. Do not grant anonymous writes or expose the service role key to the web app. The API uses the service role through its injected `fetcher` for uploads and reads; buyers read photos through `/api/i/:code/photo`.

The owner form compresses JPEG, PNG and WebP files up to 20 MB into a JPEG at most 1600 pixels on its longest edge and 512 KiB. Item details save first; a failed upload preserves those details and any existing photo. Saving again retries the photo without creating another item. Without storage configuration, item details remain usable and uploads return a friendly unavailable response. The demo stall refuses photo uploads, because its password is published and its item pages are public; the owner form says so without inviting a retry, and the item details stay saved.

Storage tests drive the Supabase requests through a stateful fake `fetcher`. On 5 November 2026 the same adapter ran against the live Supabase project from a local API with a local database: an owner added then replaced a photo, the buyer route `/api/i/:code/photo` returned the latest bytes unchanged, and an upload made with a rejected key returned 502 while the item details saved and the previous photo stayed. Storage accepted the secret key on `apikey` alone, on `Authorization` alone and on both, so the adapter's headers need no change. The bucket is private, JPEG only and 512 KiB, read back through the Storage API on 5 November 2026. A search of `apps/web` and its built bundle on 5 November 2026 found no Supabase client and no service role key. Hosted add, replace and buyer display need the main stall's owner login and have not run. Replaced photo objects remain in Storage; the database points only at the latest successful upload.

## AI questions and offers

Haggle items have AI chat for questions and offers while the stall is open and the item is available. The API uses the Anthropic provider through the Vercel AI SDK. Each buyer session gets 20 messages across items, with up to 500 characters per message. Free-text offers use the single `respond_to_offer` tool, with at most three model steps per message. Make an offer sends integer `offerPence` directly to the server; the model only words the result. A reply holding tool-call text, such as an XML-like tag, the tool's name or `_tool_result_placeholder`, is replaced with the server's fixed copy, so it is never stored, replayed to the model or shown to the buyer. The log keeps only the tag and tool names that matched, because the rest of a reply can hold buyer wording. A reply stored before this check existed is left out of the history and the buyer's transcript. Repeated tool calls in one message return the same card and spend one bargaining round.

The server computes counter-offers at 40%, 60% and 80% of the asking-to-floor gap, rounded up to 50p and capped at asking. For a haggle item, the owner's add and edit forms preview those amounts through `POST /api/owner/ladder`, which runs the same code, reads and stores nothing, and takes prices in the body so the floor stays out of request logs. The buyer must tap the server-issued card to agree. Cards and agreed prices last 30 minutes and do not reserve the item. A price edit cancels open cards and unreserved agreements, while an admitted checkout keeps its original total. Checkout accepts only an optional `agreedPriceId` and reads the amount from the database. Above-asking offers receive no new card and leave any open card live. They appear as refused-offer rows in the owner's live feed list, as do offers answered with a counter-offer.

Replies pass an amount allowlist before display. An amount written with £, GBP, pounds, quid, p or pence, or as a bare two-decimal figure with no unit after it and not stated as a plain figure in the owner's notes, must be the asking price, a card amount or agreed price, the retail reference, or an amount the buyer wrote; anything else triggers template copy instead. A card amount is any amount a card has carried for this buyer and item at the current price, so a reply may repeat an earlier counter-offer, but an edit to the item's prices makes earlier amounts unissued again. A reply that uses the words `server`, `issued` or `tool`, singular or plural, also gets template copy, unless the stall name, the item name, notes, the retail reference or this buyer's own messages for the item use that word in either form. Template copy for a counter-offer reads `I can't agree to £5. I can do £24 for it. Tap Accept if that works for you. Not paid yet.`, naming the buyer's amount when they wrote it. When a reply is replaced, the API logs `AI reply replaced by stall copy` with a `replacedBy` list of check categories (`empty`, `sale-claim`, `agreed-claim`, `system-wording`, `unissued-amount`, `amount-in-words`) and never the reply text. Replies that claim the item is paid, sold, agreed or free to take get the same template copy, which points to the offer card and the PayPal button; wording where a negation or condition governs the claim, such as `not paid yet` or `once you have paid`, stays, as do a third party's past payment such as `the owner paid a lot for it` and `the choice is yours`, and `agreed` is allowed while the buyer holds a live agreed price. The check is a fixed list of phrasings, so an unlisted rewording can still pass, such as `Payment done.` or `Help yourself.`, and an ordinary answer that looks like a claim, such as `The matching lamp has been sold.`, can still get template copy. The list is deliberately not widened further. Such wording cannot create a card, agreed price or checkout. The chat screen adds no not-paid line of its own. The pay card, which the chat screen hides, says `Take it only when this page says Paid.` once PayPal's button has loaded, as fixed copy and not model output. Buyer text counts only when currency-marked, two-decimal, or a bare number in offer wording, so dates and sizes do not count. The retail-reference amount field used by this check is `pricePence`.

The closing summary draws on the same `ai_usage` budget. It starts automatically when the owner closes the stall and again when the report's content changes, at most once per content version. Polling unchanged content does not start another summary; the API also permits a deliberate retry. A refused or failed summary leaves the plain report available. Price reviews draw on it too, with one call per review that may take 20 seconds or a second per item, whichever is longer. The Stall clerk draws on it too, with [its own limits](SPEC.md#stall-ledger).

Usage is stored per UTC day in `ai_usage`, priced at $2 per million input tokens and $10 per million output tokens, with a cache read at a tenth of the input price and a cache write at a quarter more. Across all buyer sessions and stalls, chat admits at most four turns running at once and 60 turns in a rolling minute, held in memory on the single instance of [ADR 0007](adr/0007-one-origin-the-api-serves-the-web-app.md). Past either limit the API answers 429 with `Retry-After: 60` before using a session turn or calling the model, and the buyer sees a busy message with the composer still open. Before issuing an offer card or calling the model, the API reserves an estimated $0.10 in `ai_usage`, refused once recorded usage has reached the daily cap. A refused reservation uses the session turn but issues no card and makes no model call. Provider-reported usage replaces the estimate on success, and a failed or interrupted call keeps it. The estimate is not a maximum, so admitted calls can still take spend past the cap by their own cost. One conditional update takes each turn, so concurrent requests cannot pass the 20-message cap. Calls time out after 20 seconds and do not retry automatically.

A model failure, or a refusal with words in it, returns `chatAvailable: false` on that response and uses the turn. A blank reply, or a refusal with only tool-call text, gets the server's fixed copy instead, and the question and that copy stay in the buyer's transcript. The next request tries the model again, and later prompts leave out questions that never got an answer. A reply cut off at the output limit is still shown. Session exhaustion and the daily cap hide chat while they apply. When a send fails, other than a busy 429, or chat ends, the web app closes the composer. After a failed send it also refreshes the card and agreed price, because the send can still have issued a card. `GET /api/i/:code` returns this buyer session's answered messages for the item as `messages`, so earlier answers stay behind `View your chat` after a reload and are never another session's; a buyer with no answers yet sees chat hidden. A haggle item opens on the stallholder with `Ask or make an offer` as the primary button and `Buy now` beneath it as the secondary; the checkout stays mounted behind that screen and shows when the buyer taps `Buy now`, or at once when they hold an agreed price or a checkout, or return from PayPal. A fixed-price item has no chat and pays from the item page, with the PayPal button under the owner's notes. The tag code form is on the stall home only, not on buyer item pages. Item notes, asking price and availability remain independent of chat.
