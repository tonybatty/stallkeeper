# The API is the only route to data, behind one password per stall

Reservations need row locks and transactions, which separate `supabase-js` calls cannot give, so the API connects to Supabase Postgres directly and the web app never talks to Supabase. Buyers reach data only through the API, and row-level security is not the guard: it is on for every table with no policies only to close Supabase's Data API, and the API connects as the tables' owner, which it does not restrict. With one real owner and one demo stall, Supabase Auth would add a client library for no benefit, so each stall has one password in an environment variable, exchanged for a signed HTTP-only cookie that carries the stall. The published demo password therefore opens only the demo stall. Tables stay scoped by `stall_id`, so real accounts can come later.
